## Background

本次 context 记录的是一次约 30 分钟的仓库结构调查，而不是开发规范整理。

调查目标有三项：

- 判断当前 `vassago` 仓库是否适合直接承接重构
- 分析两个历史参考仓库分别提供了什么可继承信息
- 给出下一阶段仓库结构重构的方向性结论

调查对象包括：

- 当前仓库 `vassago`
- 历史参考仓库 `mmWave-Radar-Research`
- 历史参考仓库 `vassago.bak`

## Findings

### 1. 当前仓库仍处于骨架阶段，适合现在做结构重构

调查时，当前 `vassago` 仓库的实际内容非常少：

- Git 仓库尚无 commit
- 顶层主要只有 `README.md`、`docs/`、`scripts/`、`src/vassago/`、`pyproject.toml`
- `src/vassago/` 只有最小占位包

这说明当前还没有沉没太多实现成本，因此此时重画目录边界的代价最低。

### 2. `mmWave-Radar-Research` 更像研究原型，不适合作为最终仓库骨架

调查结果显示，这个仓库更接近单条研究链路：

- 跟踪文件很少
- 目录结构以 `configs/`、`notebooks/`、`src/*.py`、`train.py` 为主
- 代码主要围绕点云采集、点云解析、数据集和训练脚本展开
- 研究脚本风格明显，工程边界较薄

它提供的主要价值不是结构，而是：

- 一条足够短的研究闭环参考
- 比较稳定、比较保守的 `cfg` 使用经验
- 以最小代价跑通“采集 -> 训练”的研究原型思路

### 3. `vassago.bak` 更像工程草稿，但结构边界不够干净

调查结果显示，这个仓库已经具备不少工程要素：

- 固件联调
- 数据采集
- 离线处理
- 文档
- 测试
- 包结构
- CLI

但问题也同样明显：

- `src` 目录承载了过多异质职责
- 统一入口把不同工作流强行堆到一棵命令树里
- 文档和流程虽然多，但阅读路径不够清楚
- “工程化元素多”不等于“仓库结构已经合理”

因此它适合作为 API、流程经验和测试思路的参考，不适合作为最终结构直接照搬。

### 4. 两个参考仓库提供的信息不同，不能混为一个继承目标

这次调查的核心判断是：

- 第一个仓库主要提供保守 `cfg` 和研究原型经验
- 第二个仓库主要提供硬件 API、采集流程、处理链路和测试经验

因此当前仓库的重构方式不应是：

- 完整继承 `mmWave-Radar-Research`
- 也不应完整继承 `vassago.bak`

而应是：

- 从第一个仓库吸收保守的 `cfg` 经验和研究闭环意识
- 从第二个仓库吸收底层 API、处理链路和测试经验
- 在当前仓库里重新组织结构边界

### 5. 第一个仓库的 `cfg` 更稳定，原因主要在配置路径而不在仓库形式

调查中一个重要现象是：

- `mmWave-Radar-Research` 中的 `profile_3d.cfg` 更接近保守、轻量的 point-cloud 输出路径
- `vassago.bak` 中的 `rd_phase1_uart.cfg` 则是 RD-over-UART 候选配置，明显更激进

造成稳定性差异的核心原因不是“第一个仓库更整洁”，而是：

- point-cloud 输出路径更保守
- UART 带宽压力更低
- 固件兼容风险更低
- RD-over-UART 路线本身更接近硬件与固件边界

因此后续需要把 `cfg` 视为独立治理对象，而不是仅仅把它们当作普通配置文件存放。

## Alternatives Considered

### 1. 直接继承 `vassago.bak` 的整体结构

没有采用。

原因：

- 其工程化元素较多，但职责边界仍不够干净
- 统一入口和 `src` 目录承担了过多职责
- 如果直接沿用，后续只会把复杂度继续滚大

### 2. 回退到纯研究脚本仓库

没有采用。

原因：

- 不利于长期维护
- 不利于多人协作
- 不利于数据契约、测试和边缘部署演进

## Consequences

这次调查直接导出以下阶段结论：

- 当前仓库应进行结构级重构，而不是在旧结构上继续堆代码
- `src` 应只承载核心库层，不再承载所有类型文件
- 根目录应为 `configs/`、`docs/`、`tests/`、`scripts/`、`data/`、`artifacts/` 等一等公民留出边界
- CLI 应视为薄层，而不是仓库结构的中心
- `cfg` 应有单独的管理策略和元信息设计

## Next Actions

- 设计 CLI 命名与职责边界
- 定义 `cfg` 元信息模型
- 定义样本、产物和实验配置的数据契约
- 设计测试分层策略
